# 角色包：把角色做成 agent skill

> 目标形态：一个角色 ＝ 一个 skill，本体直接可用（不派子代理）。与酒馆卡、世界书条目是同一真源的不同输出。

## 目录形态

```
skills/characters/<slug>/
  SKILL.md            只写用法与边界（不装角色内容——装了它就在常驻，慢慢把本体 agent 的声音压掉）
  references/01-身份.md    persona-soul 全文，零改写
  references/02-声音.md    工作规则文件的说话风格／性格锚点／对话节奏 ＋ 台词库原句 10 条
  references/03-提示词.md  卡字段原样（system_prompt／post_history／scenario／first_mes／alternate_greetings）
  references/04-边界.md    禁止项／边界 ＋ 扮演纪律
```

## 生成

```bash
python3 skills/characters/_tools/gen_pack.py --name <角色> --line twinvision|shouer --slug <slug> --title "<一句定位>"
```

- **搬运零改写**：persona-soul 整篇进 01、工作规则文件的段落进 02／04、卡字段原样进 03。要判的部分不交给脚本。
- **自称／称呼自动抽**：卡 prompt → soul → 台词库开头三来源**分别**找。别在一个来源命中就 return——只抽到自称时会把称呼丢掉（表现：SKILL.md 里写「称对方『待补』」）。
- **人工只补两处**：一句定位、`02` 末尾「最容易演坏的地方」三条。这两样脚本判断不了。
- **重跑覆盖 02**：脚本发现 02 已被手改会先挪成 `.bak`；重跑完要按 `.bak` 把人工补的三条补回去。

## 选角色：先查撞名

**角色自称与本体 agent 的自称重合的，别拿来做本体实验体。** 同一上下文两个同名，声音必串，而且切回来没有信号。

- 撞：自称与本体同一个词的角色——写的时候分不清哪句是谁的，回正也回不干净。
- 不撞：自称「我」「本小姐」的角色——切换靠人称就有信号（「我」＝她，本体那个自称＝本体）。
- 再看声线距离：跟本体腔调差得越远越安全（短句／零语气词／零感叹号 vs 长句／反讽）。差得远的两个不容易互渗。

## 叠层风险（必须写进 SKILL.md 的边界，不能省）

1. **同名污染**——两个同名角色叠久了，口癖互相渗。
2. **规则过载**——references 上千字压下来，模型开始「遵守规则」而不是「演」，越守越平。
3. **注意力中段塌陷**——本体只有一条 system 消息，没有酒馆的注入顺序与 token 预算调度；四件全倒进来，中间那层最容易被忽略。
4. **不可逆**——加载过的痕迹留在本次会话里；酒馆开新对话就干净，本体不行。这是不派子代理的结构性代价。
5. **真源漂移**——persona-soul／工作规则文件／卡／包四处并存，改一份不同步就漂。

**适用边界**：短回合可以（一两段对话、对台词、写卡时校准声线）；长扮演、十几轮不换气不行，走子代理或酒馆。操作纪律：一次会话只加载一次；按用途只取一件 reference；连演 8 轮自检（感叹号冒没冒、「我／你」漏没漏、有没有变成温柔的妈、口癖有没有渗进本体）。

## 包要写薄

无口、一句顶一句的角色，references 写厚＝包自己把声线破坏掉：规则一厚就诱导长篇。这类包只留硬规则 ＋ 原句锚 ＋ 对错表，不铺理论。

## 与技能条（世界书条目）的分工

| | 世界书条目（卡内书／共用书） | agent 角色包 |
|:--|:--|:--|
| 跑在哪 | 酒馆会话 | 本体／子代理 |
| 触发 | 关键词／正则，人配 | 语义判断 |
| 能做什么 | 只能「按流程说话」，不执行 | 可调工具／脚本／档案 |

两种形态可以并存，**真源只一份**（persona-soul／工作规则文件），两边都是生成物。
